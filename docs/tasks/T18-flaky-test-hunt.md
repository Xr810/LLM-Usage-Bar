## 0. 已知事实(不要重复验证,直接从这里接)

2026-08-14 到 08-15 期间,全量 `cargo test` 出现过 **5 次单次失败**,
每次重跑都消失,**5 次都没抓到测试名**:

| 时间 | 分支 | 表现 |
| --- | --- | --- |
| T2 复核 | `task/T2-subscription-split` | `FAILED. 1150 passed; 1 failed` |
| T1 自查 | 主工作区 | `usage_dashboard_commands` 二进制被 SIGKILL |
| T5 自查 | `task/T5-failure-classify` | `identity_migration` 的 symlink 测试(**唯一一次拿到名字**) |
| T11 复核 | `task/T11-async-upstream-auth` | `FAILED. 1222 passed; 1 failed` |
| T14a+T15 复核 | `main` | `FAILED. 1250 passed; 1 failed` |

**最后这次是在安静的机器上发生的** —— 没有其他 agent 在编译。
所以「并发抢共享 cargo target」这个解释**已经被推翻**,不要再用它。

复现率粗估 **1/11**(最后一次之后连跑 10 轮全绿)。

---

## 1. 要回答的三个问题

1. **是哪个(哪些)测试?** —— 名字。这是最重要的产出
2. **它是真随机,还是对并发顺序敏感?** —— `--test-threads=1` 下还挂不挂
3. **它依赖什么外部状态?** —— 真实 `$HOME`、系统时间、文件系统 mtime 分辨率、
   端口、钥匙串……

---

## 2. 怎么做

### 2.1 先把失败信息完整捕获

之前五次都没抓到名字,是因为 grep 模式太窄。**这次把完整输出落盘**:

```bash
pnpm rust -- test --manifest-path src-tauri/Cargo.toml > /tmp/run-$i.log 2>&1
```

失败那次的日志**完整保留**,报告里贴 `failures:` 那一段。

### 2.2 跑够轮数

按 1/11 的复现率,**至少 40 轮**才有把握抓到。写一个循环,失败就停下来保留现场。

**这一步会跑很久,是预期的。** 不要为了快而减少轮数。

### 2.3 抓到之后,做对照

拿到名字后跑三组对照,每组 20 轮:

| 组 | 命令 | 想区分什么 |
| --- | --- | --- |
| A | `--test-threads=1` | 是不是并发顺序敏感 |
| B | 只跑那一个测试(`test <name>`) | 是不是自身不稳定 |
| C | 只跑它所在的模块 | 是不是被同模块的邻居污染 |

### 2.4 读代码找根因

拿到名字和对照结果之后,**读那个测试和它测的代码**,找出它依赖的外部状态。
已知的三个嫌疑方向(仓库里确实存在这类测试):

- **真实 `$HOME`**:`identity_migration` 那次就是对真实 `~/.cc-switch` 做前后快照
- **文件系统 mtime 分辨率**:仓库里有测试显式设 mtime(`filetime` 是 dev-dependency),
  CI 上秒级分辨率会让同秒先后测不出来
- **`serial_test`**:仓库用了它,**没标 `#[serial]` 但共享全局状态的测试**
  会在并发下互相踩

## 3. 明确不要做的事

- ❌ **不要修它。** 本任务只出诊断报告。改法要我看过根因再定
- ❌ 不要给测试加 `#[ignore]` 或 `#[serial]` 让它「不挂了」——
  那是把问题藏起来,不是解决
- ❌ 不要改任何生产代码
- ❌ 不要因为跑了 20 轮没复现就下「不存在」的结论 ——
  40 轮没复现只能说「本轮未复现」,并给出你实际跑了多少轮

不走 README §3 的常规格式,交这四样:

1. **测试名**(抓到了就是抓到了;没抓到就说跑了多少轮没抓到)

(说明复现率比 1/11 更低,或者与某个已经消失的条件有关)。
