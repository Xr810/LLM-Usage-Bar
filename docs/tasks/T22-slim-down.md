## 0. 背景:为什么现在是做这件事的时候

后端刚连做了 19 个任务(T1–T20),期间为了让每一步都能单独复核,**有意留下了一批
「暂时这样」的东西**:转发层、`#[allow(dead_code)]`、只搬不删的旧路径。
现在整批做完了,该回头收一次。

**已知的一个实锤**(2026-08-15 实测):`src-tauri/Cargo.toml` 里有 **11 个依赖在
`src-tauri/src` 里 0 引用**:

```
httparse  tokio-rustls  hyper-rustls  webpki-roots  rustls-native-certs
http-body-util  hyper-util  tower-http  json5  json-five  rquickjs
```

**但不要直接删。** 其中一部分可能是被别的 crate 当作 feature 开关或传递依赖需要的
(TLS 那几个尤其可疑,reqwest 的 rustls 特性可能需要它们在场)。**逐个删、逐个验**。

## 2. 允许动手改的范围

诊断清单交完之后,**只动这三类**:

1. **0 引用的依赖** —— 逐个删、逐个 `pnpm rust -- check` 验证,删不掉的留下并说明
2. **已经可以摘掉的 `#[allow(...)]`** —— 摘掉之后编译器不报警才算数
3. **确认无人引用的转发层文件**

**不许动的**:任何函数体逻辑、任何测试断言、任何 SQL 语义、任何 schema。
第 4/5/6 类即使发现了冗余也**只出报告不动手** —— 那些要合并需要判断,由项目所有者定。

## 3. 性能:先量再说,不要凭感觉优化

这个项目对能耗敏感(见 `HANDOFF.md` §11,那一轮做过实测)。**不要凭直觉改。**

已知的两处值得量一量:

- **T13 的 SSE 旁路缓冲**:`route/server.rs` 里每个在飞的请求最多留 256 KB
  (`MAX_SSE_EVENT_BYTES`),用于非流式兜底解析 usage。**并发 10 个请求就是 2.5 MB。**
  能不能按 `content-type` 判断,是 `text/event-stream` 就完全不攒?
  (T13 想过但忍住了,理由是统一路径更简单 —— 现在可以重新评估)
- **启动路径**:app 启动时做了多少事?有没有能延后到真正需要时再做的?

**报告里给数字**,不要给「感觉会快一点」。量不出差别的就说量不出。
