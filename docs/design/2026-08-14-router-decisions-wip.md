## 7. 2026-08-14 实测:router 的第一理由消失了

用户最初要 router 的理由是「**保留 Codex 官方登录,但模型流量走自己的 provider**」
(远程操作 + 官方插件 + 第三方模型,三者同时要)。当天在他本机逐步实测,结论是
**这件事纯配置就能做到,不需要任何 router**。

### 7.1 关键发现:`requires_openai_auth`

对比他 6/3(CC-Switch 时期,远程/插件可用)与 8/14(手写配置,远程/插件不可用)
两份 `config.toml`,差别只有一处:

| | 6/3(能用) | 8/14 改之前(不能用) |
| --- | --- | --- |
| `requires_openai_auth = true` | ✅ 有 | ❌ 没有 |
| `experimental_bearer_token` | ❌ 没有 | ✅ 有 |

`auth.json` 两边**逐字段一致**(`auth_mode: chatgpt` + `OPENAI_API_KEY: null` +
`tokens` + `last_refresh`)——问题从来不在 auth.json。

**能用的配置形态(实测通过):两个键都要。**

```toml
model_provider = "packyapi"

[model_providers.packyapi]
name = "packyapi"
base_url = "https://www.packyapi.ai/v1"
wire_api = "responses"
requires_openai_auth = true            # 维持官方会话 → 远程 + 插件可用
experimental_bearer_token = "..."      # 模型请求的实际认证
```

只有 `requires_openai_auth` 而没有 bearer token 时,Codex 会拿官方 OAuth token 去
请求 provider,packyapi 回 `401 无效的令牌`。两个都在才成立。

**provider id 不是关键**——6/3 用的是 `openrouter`(厂商名),攻略示例用 `custom`,
两者都能用。曾经怀疑过 id,已证伪。

### 7.2 实测:官方 OAuth token 没有外泄

把 `base_url` 临时指向本地一次性监听,抓一次真实请求的头(只对头值算 sha256 与
已知凭据比对,不打印、不落盘 token,请求体只数字节):

```
authorization: [58 字符] → 中转的 bearer token     ✅
session-id:    [36 字符] → 不是任何已知凭据(UUID)
```

官方的 access / id / refresh token 与 account_id **一个都没出现**。

**未验证的一项**:`x-oai-attestation` 头当时没被纳入指纹比对(筛选关键词写的是
`openai`,没匹配到 `oai`)。它是否携带与官方会话相关的材料**未知**,想确认需要
重跑一次同样的抓包流程。

### 7.3 由此,router 现在的理由只剩两条

1. **自动故障转移**——一家挂了自动换下一家。纯配置做不到,必须有东西在请求路径上
2. **纵深防御**——把官方凭据拦在 localhost。但 §7.2 实测显示当前**并没有在漏**,
   所以这条是「以防万一」,不是「正在出血」

用户 2026-08-14 表示这两个功能他确实需要,router 仍然要做,但**要先权衡代价**(见 §8)。

### 7.4 顺带修掉的一个事故

测试过程中 Codex 报 `refresh token was already used`。原因:`~/.codex/auth.json`
与 `auth.json.bak-before-packyapi-20260812-105326` **逐字节相同**——文件停在 8/12
02:21 的状态,里面的 refresh token 早已被用掉(一次性)。之前一直走 bearer token,
用不到 OAuth 续期,所以没暴露;打开 `requires_openai_auth` 后第一次真的用到就炸了。
重新登录即修复。

**与本 app 无关**:装着的 8/07 构建里确实有 `auth.openai.com/oauth/token` 和 Codex
的公开 client_id,但它们属于 `credentials/codex_oauth_auth.rs`——app 自己的托管
OAuth 账号管理器,凭据存在自己的 `codex_oauth_auth.json`,**不碰 `~/.codex/auth.json`**。
(昨天从额度链里删掉的 `refresh_codex_cli_token` 确实读 CLI 的 auth.json,删得对,
但那段代码从未进过已安装的构建。)

**要留意**:用户的 `codex-provider` 脚本在切换时会备份 `config.toml` / `auth.json`。
如果它也会**恢复** auth.json,重新登录后再切一次 provider 会把 refresh token 打回
旧状态、再次触发同一个错误。尚未查证该脚本是否真的恢复 auth.json。

## 8. router 的能耗与内存(2026-08-14 已量,结论:不构成否决理由)

用户提出「加一个 router 对能耗和 RAM 影响多大」,当天在他本机量了基准并估算。

### 8.1 基准(实测)

```
LLM Usage Bar (已安装的 2026-08-07 构建)
  RSS        38.1 MB
  运行       12 小时 29 分
  累计 CPU   46 分 28 秒  →  平均 6.2%  →  约 5,360 秒 CPU/天
```

**顺带发现的事**:HANDOFF §11.3 把「轮询浪费约 1,382 秒 CPU/天」当作首要问题修掉,
而这个构建是 8/07 的,**早于那五项优化全部合入(8/13)**。也就是说用户现在跑的是
未优化版本,实测烧的是那个数的约四倍。**重装一次新构建的收益比 router 的开销大
三个数量级。** 用户 2026-08-14 表示暂时不构建,此项待办。

### 8.2 内存

router 跑在 app 进程内,tokio 运行时已存在,边际成本只有三块:

| | 大小 |
| --- | --- |
| 监听器 + 路由表 + 拉黑状态 | < 1 MB |
| 每个进行中的请求(纯流式转发) | 一个缓冲块,几十 KB |
| 每个进行中的请求(**要能重发**) | 等于请求体大小 |

第三行是故障转移这个功能**本身要求**的:要重发给下一家,手里就得有请求体。
实测用户单个请求体 **58 KB**,但 Codex 每轮重发整段对话,长会话会涨到几百 KB 至几 MB。

**第 15 条(已吐字之后不换)天然限制了它的寿命** —— 缓冲只需留到第一个字节回来,
通常 1–3 秒,不是整个流式过程。峰值几 MB、存活几秒,在 38 MB 基础上是零头。

### 8.3 CPU

**空闲为零** —— 监听 socket 挂在 kqueue 上不产生唤醒。这与轮询有本质区别。

每个请求(不含协议转换):

| 动作 | CPU |
| --- | --- |
| 改模型 ID(解析 58 KB JSON) | ≈ 1.8 ms(按仓库自己的基准 37 MB/1.1s = 33 MB/s 折算) |
| 上游 TLS 握手(连接复用后摊薄) | 2–5 ms |
| 搬字节 | 微秒级 |
| **合计** | **2–8 ms** |

按 200 次请求/天 ≈ **1 秒 CPU/天**,对照 8.1 的 5,360 秒/天,差三到四个数量级。

### 8.4 真正该防的三件事(都不是吞吐)

1. **连接泄漏** —— 内存与文件描述符稳定爬升,这才是现实的失败模式
2. **绝不加定时器** —— router 必须纯事件驱动。任何心跳/健康检查的定时器都会阻止
   系统进入空闲,那才是真耗电(§11.3 的教训)
3. **缓冲上限** —— 建议 4 MB;超过就退化成不可重发的纯流式,否则超长上下文能把内存顶上去

## 9. 协议转换:v1 不做(2026-08-14 决定)

| # | 决定 |
| --- | --- |
| 19 | **v1 不实现 Responses ↔ Chat Completions 转换** |
| 20 | 但**每个 provider 的协议必须记录在配置里**,并在**配置阶段拦住混协议的队列**——报一句看得懂的错,而不是留到运行时诡异失败 |

**理由不是性能。** 转换的 CPU 代价实测估算:请求方向约 4–6 ms(解析 + 重组 + 序列化),
响应方向约 0.5–1 ms/秒(流式每块都要转)。一次 30 秒的回答总共 30–40 ms,一天 200 次
约 6 秒 CPU/天 —— 仍是噪声。

**真正的理由是维护成本。** 转换有损且脆弱:工具调用形状不同、reasoning 在 Chat 侧
可能没有对应物、流式事件生命周期不同(Responses 要跨块维护 `output_index` /
`content_index` 并凭空造生命周期事件)、两边都在加新字段导致转换器持续腐烂。
本仓库历史就是证据——除转换本身还长出了 web_search 黑名单、`base_instructions` 必填、
`supportsParallelToolCalls` 等一串补丁。

**「智能识别、同协议就跳过」这个方案被否掉了**,理由是它省错了东西:

| | 要写转换器吗 | 队列能混协议 | 运行开销 |
| --- | --- | --- | --- |
| 甲 不做转换(**选中**) | ❌ | ❌ 必须同协议 | 最低 |
| 乙 做,总是走 | ✅ | ✅ | +30 ms/次 |
| 丙 做,同协议跳过 | ✅ **还是要** | ✅ | 甲乙之间 |

只要队列里**可能**出现协议不同的两家,转换器就还是得写、得维护;跳过只是有时候不跑它。
而运行时那几十毫秒本来就是噪声。丙 是三者中性价比最差的:复杂度按乙算,收益按毫秒算,
还多一条代码路径要测。

用户当前两家(packyapi 与官方)都是 `wire_api = "responses"`,队列天然同协议。
以后真要加 DeepSeek / Kimi 这类 Chat-only 的,再往上加一层,不用推翻任何东西。

## 10. v1 的范围,以及它到 v2 的路(2026-08-14 决定)

| # | 决定 |
| --- | --- |
| 21 | **v1 只做「一个全局 provider 顺序」**,不做每模型独立排序;第 9 条降级为 v2 |
| 22 | 但 v1 **照样需要「哪家有哪个模型 + 真实模型 ID」** —— 故障转移切过去的那家未必有这个模型(官方就没有 `sol`),不知道就只是换个地方 400 |
| 23 | **硬约束**:路由决策函数必须返回「**这个模型的候选队列**」,不能返回「当前的 provider」 |

第 23 条是让 v1→v2 保持增量的关键:

```rust
// 这样写，v2 只是给 order 多一个来源
fn candidates(model) -> Vec<(Provider, 真实模型ID)>

// 这样写，v2 就是重写
fn current_provider() -> Provider          // ← 禁止
```

第二种把「全局只有一个当前 provider」焊进签名,所有调用方都会跟着这个形状长,
到 v2 每个调用点都要改。第一种从一开始就承认候选是按模型算的,只是 v1 阶段所有
模型算出来碰巧一样。**代价为零,只是写的时候多想一步。**

v2 要加的只是一个 `??`:

```
v1:  order(任何模型) = 全局顺序
v2:  order(模型 M)   = 该模型的专属顺序 ?? 全局顺序
```

真正会变的是**配置界面**(provider 列表排序 → 每模型排序入口)和**存储**(多一张
「模型 → 专属顺序」表),都是加,不是改。

**顺带定下的语义**:换到第二家之后,下一次请求**仍然从头评估队列**;「继续用第二家」
这个效果由**拉黑**产生(第一家在冷却期内自然被跳过,冷却结束自动恢复试探)。
不需要额外的「当前是谁」状态,v2 完全沿用。与第 13、14 条一套。

## 11. 用量与余额的来源(修正第 17 条)

### 11.1 为什么第 17 条不成立

原第 17 条说「router 只记选了谁、不记 token」,理由是怕与会话日志双计。但查证发现
会话日志摄入是这样绑定的:

```rust
db.with_bound_usage_source("codex", provider_id, ...)
```

**Codex 的会话用量被整体绑定到一个 provider**,不区分某次请求实际走了哪家。于是:
日志有 token 没归属,router 有归属没 token——**谁都答不出「packyapi 用了多少」**。

### 11.2 修正后的决定

| # | 决定 |
| --- | --- |
| 17′ | **router 记 token**(它是全 app 唯一同时知道 token 与 provider 的地方,token 就在响应体的 `usage` 里),但**独立成表**,语义是「按 provider 分账」 |
| 24 | 会话日志那份继续管**总量**(覆盖不走 router 的部分:桌面版、其他工具);两张表**回答不同问题,UI 上不相加** |
| 25 | **余额优先问 provider 的 API** —— 权威,且能覆盖用户在本机之外的消耗 |
| 26 | 没有余额 API 的:用 router 累计 + **用户录入、可编辑的价格表**估算。仓库已有 `provider_model_pricing` 可扩展 |
| 27 | 估算值**必须在 UI 上与接口读数视觉可辨**,且注明它**只计经过 router 的部分**——它是**下界**,不是余额 |

第 27 条不是洁癖:估算永远偏低(同一个 key 在别的机器/工具上的消耗看不见),两者
长得一样的话,迟早会拿一个下界当余额用,然后突然欠费。

### 11.3 UI 形态(用户指定,已出样)

按量计费 provider 的卡片有**上下两条量表**:

```
今日花费    $3.20 / $10.00      ← 流量：每天归零，分母是用户设的每日限额
▓▓▓░░░░░░░

余额        $61.40 / $100.00    ← 存量：只减不增，分母是参考额度
▓▓▓▓▓▓░░░░
上次充值 $100 · 2 分钟前更新
```

- 分母来源:接口能读就读;读不到由用户手动设(通常是「上次充值的金额」)
- **分母会过期**:接口读数发现余额**变大**时,应当认为是充值,把分母自动重置成新余额;
  否则充值后进度条会显示 180%
- 两条性质不同(流量 vs 存量),视觉上要能区分
- 估算卡片:徽章 + 虚线边框 + 暖色,一眼看出不是读数

订阅型 provider(官方)**不适用**这个布局——它没有余额概念,继续用现有的窗口量表。
`BillingKind::Subscription` 与 `Metered` 的区分本来就在。

## 12. 自动 / 手动两个模式(2026-08-14 决定,取代旧 §12)

原来的问法是「手动选择到底是置顶(软)还是锁定(硬)」——用户给了更好的答案:
**把意图做成显式的模式,而不是从一次点击里猜。**

| # | 决定 |
| --- | --- |
| 28 | 拉黑在 UI 上显示为「**暂不可用 · 还有 X 分钟**」。两个模式都显示:自动模式下它解释「为什么跳过了这家」,手动模式下它只是给用户的提示 |
| 29 | **两个模式**。自动(默认):按配置顺序走,失败自动换下一家,拉黑生效。手动:只用你选的那一家,**不自动切换**,失败就是失败、你看得见,拉黑只显示不生效 |
| 30 | **必须能看出实际在用哪家**。自动模式下是刚需(否则自动降级后用户以为在官方上,账单出现在中转那边) |
| 31 | **手动模式必须持续可见**,不是切换时提示一下就完。否则哪天切了忘了,某家挂了没自动换,用户会以为故障转移坏了 |
| 32 | 手动模式下**照样记录失败,只是不据此行动**。切回自动时 router 手里已有新鲜的健康信息,不用重新踩一遍 |
| 33 | **不做「N 小时后自动切回自动模式」**。用户切手动就是因为要自己说了算,系统不该偷偷把方向盘拿回去;靠第 31 条的常驻标识提醒即可 |

「手动模式」就是之前纠结的那个「锁定」,只是它是一个**模式**而不是每家一个 flag。
它也正好实现了用户描述的行为:「就算标注了暂不可用我依旧可以切换,我发现不行了自己
会换回去的」——切手动、试、失败、换回去。以及「我想看看官方修好没有」这个场景:
切手动模式去试,得到的答案才是真的(自动模式会把失败悄悄兜住,毁掉这个答案)。

## 12.1 手动切换只改 router 内部,不碰 config.toml

这是把「手动切换」和「绕过 router」彻底分开的关键,**并且撤销了之前的路 A**。

| # | 决定 |
| --- | --- |
| 34 | **config.toml 的指针写一次之后永不再改**,永远指向 router。手动切换改的是 **router 内部的选择**,不是配置文件 |
| 35 | **撤销「app 退出时把指针改回直连」(路 A)** |

**为什么撤销路 A** —— 它买到「app 挂了 codex 还能用」,代价却是:

- 绕过 router 变成**设计里的常态**,那段时间的用量没有归因记录
- 要补一整套「指针时间线 + 按时间窗给会话日志补归因」的机制
- **复写配置又回来了**——而消灭复写正是用户最初要这个方案的原因

这笔账不划算。而「app 挂了那几十秒」用户早就接受过:「撑死了也就是退出或者升级
那几十秒,正常又不会去改它」。路 A 是我后加的补丁,现在撤掉。

**于是会计漏洞消失了**:流量永远经过 router,记录永远完整。不需要时间线,不需要
持续监听 config.toml。

## 12.2 逃生门:降级为异常操作

手动改 config.toml 指回中转的能力**依然保留**,但性质变了——从「设计里的常态」
变成「router 彻底坏掉时的自救」。于是会计缺口也从「每天都在漏」变成「你自救的那
段时间没记录」。

| # | 决定 |
| --- | --- |
| 36 | app 启动时若发现指针不是自己写的那个:**不要静默覆盖**,标记「上次到现在这段有缺口」,把受影响 provider 的估算标成不完整,并提示用户。一个标记,不是一套系统 |
| 37 | **逃生门不能只存在于「需要 app 活着才能用」的地方**。必须有一条命令行的回退方式并写进文档——app 都挂了,app 里的按钮点不了 |

第 37 条是这一节里最容易被漏掉的一条。
