## 0. 请先读这一节:这次要你产出什么、不要产出什么

这个 app 的界面是 **macOS 原生 SwiftUI**,不是网页。它已经有一份视觉规范
(`NativeDesignSystem.swift`)和一份正在执行的 HIG 改造计划,那份计划的原则是:

> **标准交互用系统控件,展示性内容自绘但用系统的材质和 token。**

所以颜色、字号、圆角、间距**已经有出处了**,不需要你再定义一套:

| 层 | 来源 | 你要不要管 |
| --- | --- | --- |
| 颜色 | `Color.accentColor`(跟随用户系统强调色)、`.windowBackgroundColor`、`.separatorColor`、`.regularMaterial` | ❌ 不要出色板 |
| 字号 | macOS 语义刻度 `.title/.title2/.headline/.body/.callout/.subheadline/.footnote` | ❌ 不要出字号表 |
| 圆角 | 4 档,全部 `.continuous` | ❌ |
| 间距 | 8pt 网格 + 半档:4/8/12/16/20/24 | ❌ |
| **布局与信息层次** | —— | ✅ **这是你的活** |
| **状态清单(空/错/中间态)** | —— | ✅ **这是你的活** |
| **文案** | —— | ✅ **这是你的活** |

**明确的禁忌**(都是这个项目已经踩过的「一眼看出是网页」):

- 米白暖色背景(`#F8F7F4` 这类)—— macOS 是中性灰
- 自定义品牌靛蓝当交互色 —— 交互元素要跟随系统强调色
- popover 里套卡片、Web 那种宽松内边距
- 小于 10pt 的字
- 只靠红/黄/绿传达状态 —— 系统有「不使用颜色传达信息」开关,状态**必须同时有形状或 SF Symbol 区分**

**对标物**:系统设置、控制中心、菜单栏的 Wi-Fi / 电池菜单。不是 Vercel / Linear。

**其他硬约束**:

- 四语言(中 / 英 / 日 / 德),**德语最长**,label 列不能溢出
- 浅色 / 深色 × 增强对比度 × 降低透明度 × 降低动态效果,都要成立
- 全键盘可达,VoiceOver 逐行读出来要是一句完整的话

## 1. 这个面板是什么(一句话心智模型)

一个跑在本机的 router。它拦下 Codex CLI 发出的请求,按用户配置的顺序转给某一家上游
provider,失败了自动换下一家,并把 token 记到对应那家的账上。

用户为什么要它:手上有官方订阅 + 若干中转,想按模型和价格决定每次请求走哪家,
而且要能看出**钱实际花在了哪**。

---

## 2. 四个页面,顺序不能改

这个顺序是被真实运行验证钉死的,不是偏好:

1. **provider + 模型映射编辑页** —— 没有映射,router 对一切请求 503,后面全是空转
2. **凭据入口** —— 把 key 绑到 provider
3. **指针状态 + 启用按钮** —— 会真的改用户磁盘上的文件
4. **模式开关 + 分账面板**

四屏可以是同一个设置 pane 里的分区,也可以是独立页面 —— **这正是要你判断的事之一**。
参考:现有设置窗是三个 pane 的 TabView(通用 / providers / 诊断),路由是第四块内容,
它比另外三块都重。

## 3. 页面一:provider + 模型映射编辑页

### 数据形状(后端已固定)

```
Provider {
  id: String                     // 用户可见的短标识
  displayName: String
  baseUrl: String
  wireApi: "responses" | "chat_completions"
  priority: Int                  // 越小越先试
  enabled: Bool
  authKind: "chatgpt_oauth" | "bearer_key" | "none"
  credentialKeyId: String?       // 指向凭据表的引用,不是 key 本身
}

ModelRoute {                     // 按 provider 分组,全量替换
  logicalModel: String           // Codex 发过来的模型名,如 gpt-5.6-sol
  upstreamModel: String          // 这家实际认的 ID
}
```

### 已定的产品决定(编号是设计文档里的,别推翻)

| # | 决定 | 对设计的含义 |
| --- | --- | --- |
| 8 | 录入分两步:**先加 provider(带模型清单),再按模型排顺序** | 两步不能糊成一个大表单 |
| 11 | 模型清单能自动拉就自动拉(各家 `/v1/models` 格式不同),**手动贴保底** | **手动是保底不是降级** —— 不能把手动做成灰色小字里的二等入口。有些 provider 永远拉不到 |
| 12 | **表里一行不带开关**(不要每行的协议/搜索之类的开关) | 保持行的极简 |
| 21 | v1 **只有一个全局 provider 顺序**,不是每模型独立排序 | 但布局不能把「全局唯一顺序」焊死 —— v2 要加每模型顺序 |
| 7 / 22 | 上游模型用**各家真实 ID**,不发明新名字 | 「哪家有哪个模型」是用户必须能看清的信息。官方就是没有 `sol`;不知道这点,切过去只是换个地方 400 |
| 10 | **严格按顺序,不做负载均衡** | 顺序是有意义的,要能表达「第一家、第二家」而不是一堆平级卡片 |

### 必须设计的状态

- **一个 provider 都没有**(全新用户)—— 要说清「router 现在对一切请求返回 503」,
  而不是一句「暂无数据」
- 有 provider,但**这个 provider 一条模型映射都没有**
- `authKind = bearer_key` 但 `credentialKeyId` 为空 —— 这家其实用不了,要一眼看得出
- `enabled = false` 的 provider 怎么和启用的区分
- 排序交互:拖拽?上下箭头?这条要你给判断,注意全键盘可达
- 保存失败:`wireApi` / `authKind` 非法值会被后端拒(错误文案是中文)

## 4. 页面二:凭据入口

### 不可协商的安全约束

后端的输入输出结构体里**永远不会出现凭据明文**。router 只认 `credentialKeyId`
这个引用,真正的 key 走仓库既有的凭据命令存进钥匙串。

**对设计的直接后果:key 一旦存进去,界面就再也显示不出来了。** 不能设计成「一个
带眼睛图标可以查看的密码框」。能做的只有:

- 显示「已绑定」+ 来源描述(哪个钥匙串条目)
- 「替换」(重新输入一次)
- 「解绑」

### 三种 authKind 的界面差别

| authKind | 需要 key? | 界面 |
| --- | --- | --- |
| `chatgpt_oauth` | 否,走官方登录 | 不该显示 key 输入 |
| `bearer_key` | 是 | 未绑定时这家不可用 |
| `none` | 否 | 少见,但要能表达 |

## 5. 页面三:指针状态 + 启用按钮

### 数据形状

```
PointerState {
  state: "ours" | "not_ours" | "unreadable"
  current: String?    // not_ours 时当前指向谁;从未配置过则为空
}
```

三态的语义:**已接管** / **未接管**(当前指向 `current`,或者从来没配过)/ **读不到**。

### 这一屏最重要的三件事

1. **点「启用」会真的改用户磁盘上的 `~/.codex/config.toml`。**
   这不能是一个不起眼的 toggle。用户必须在点之前就知道自己在授权一次文件写入。
   怎么表达而又不吓人 —— 这是要你解决的设计问题。

2. **点完必须提示用户重启 Codex。**
   Codex 不会重读 `config.toml`,这是有意的设计选择。用户不会知道这件事。
   **一个会自己消失的 toast 不够** —— 用户错过了就会以为路由坏了。

3. **「指针缺口」要能表达。**
   如果指针曾经不指向我们(用户手动改过、或别的工具改过),那段时间的用量没经过
   router,**受影响 provider 的用量估算是不完整的**。后端记了这个缺口的起始时刻。
   界面要能说明「从 X 时刻起,这几家的数字偏低」。

## 6. 页面四:模式开关 + 分账面板

### 模式

值是 `"auto"` 或 `"manual:<providerId>"`。

| # | 决定 | 对设计的含义 |
| --- | --- | --- |
| 29 | **两个模式**。自动(默认):按顺序,失败自动换,拉黑生效。手动:只用选中那家,不自动切换,失败就是失败,拉黑只显示不生效 | 是模式,不是每家一个 flag |
| 31 | **手动模式必须持续可见**,不是切换时提示一下 | 切了忘了 → 某家挂了没自动换 → 用户误判成「故障转移坏了」。这是个持久的状态指示,不是一次性提示 |
| 30 | **必须能看出实际在用哪家**,菜单栏里就要能看出 | 自动降级之后用户以为还在官方,结果账单出现在中转那边 |
| 28 | 拉黑显示为「**暂不可用 · 还有 X 分钟**」,**两个模式都显示** | 自动模式下它解释「为什么跳过了这家」;手动模式下只是提示,用户照样可以选它 |
| 33 | **不做「N 小时后自动切回自动」** | 用户切手动就是要自己说了算,系统不该偷偷把方向盘拿回去 |
| 13 | 拉黑单位是**模型 × provider 那一行**,不是整个 provider(只有连不上/超时这类与模型无关的失败才拉黑整家) | 「暂不可用」可能只针对某个模型 |

### 分账面板

```
RouterUsageSummary {           // 按 provider 汇总,时间范围是半开区间
  providerId: String
  attempts: Int
  failures: Int
  inputTokens: Int
  outputTokens: Int
}
```

**这一段是整份委托书里最容易被做错的地方:**

> 这个数字是**下界**,不是余额,也不是账单。
> 它只统计「经过 router 且成功抓到 usage」的请求。用户中途取消的、上游断流的、
> 上游根本不发结束事件的,**全部缺席**。

**所以界面绝不能长得像一张账单。** 它得让用户一眼理解「实际花费 ≥ 这个数」。
怎么在不啰嗦、不每行都挂免责声明的前提下把这件事说清楚 —— 这是本屏的核心设计问题。

(这个项目里已经有一套区分「读数 vs 估算」的处理:估算卡片用徽章 + 虚线边框 + 暖色。
可以沿用这个思路,但分账是**第三类**:它是真实计数,只是不完整。)

## 7. 明确不在这一轮的

- **按量计费 provider 的双量表卡片**(今日花费 / 余额,流量 vs 存量)—— 已有设计,不重做
- 现有用量仪表盘、菜单栏 popover 的整体重设计 —— 那是另一条线(HIG 改造 P3/P4)
- 色板和字号刻度 —— 见 §0
- 协议转换(v1 不做,Responses ↔ Chat Completions 不互转)
