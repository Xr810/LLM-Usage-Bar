## 0. 全部做完之后,这个 app 是什么

只讲能实现什么,不讲怎么实现。下面所有决策服务的是这个目标。

### 它替你盯着所有 AI 工具的用量和花费

你照常用 Claude Code、Codex、Gemini,它在旁边记账,不打扰你。

菜单栏常驻,一眼看到当前状态。想细看就打开面板:每家 provider 分别承担了多少、
每个模型花了多少、时间范围对比、热力图看使用节奏。花费按价格表折算成钱。

订阅类的显示 5 小时窗口与 7 天窗口还剩多少、何时重置。按量计费的显示两条:
**今天花了多少 / 每日限额**,以及**还剩多少 / 你充的额度**。有余额接口的读接口,
没有的按用户录入、可改的价格表估算——**估算明确标出**,不会让人把下界当余额用。
超预算或额度见底会提醒。

### 它替你决定每次请求走哪家

同一个模型底下可以挂多家(官方、中转、以后自建的 VPS),排个优先级,之后不用管。

某家挂了、限流了、额度耗尽了,**自动换下一家**,CLI 侧毫无感觉。挂掉的那家进冷却,
过一会儿自动再试。界面上能看见每家是「可用」还是「暂不可用 · 还有 4 分钟」。

### 但方向盘随时能拿回来

切到手动模式:只用指定的那一家,**系统不自作主张**,失败就是失败、看得见。

这在验证某件事时是关键的——比如「官方修好了没有」,自动模式会把失败悄悄兜住给出
假答案。只要处在手动模式,界面会一直显示着,不会切了忘了。

### 它不碰原有的东西

Codex 官方账号照常登录,手机远程操作与官方插件全都能用,**同时**模型流量走自己的
供应商。配置只写一次,之后永不再动。万一 router 出问题,有一条**不依赖 app 存活**
的命令能立刻退回直连。

### 账目是一笔明白账

每一家分别花了多少、承担了多少请求、失败过几次,都记着。不会出现「Codex 一共用了
这么多,但不知道哪些走了中转哪些走了官方」——**而这正是今天的状态**。

> **一句话**:配一次,之后不用再想「现在该用哪家、那家还有没有额度、这个月花了多少」。
> 它替你切、替你算,而你随时能接管。

**当前完成度**:监控、面板、订阅窗口、每日预算、账号管理已经在跑;**router 相关全部
尚未实现**。

## 1. 需求

用户 2026-08-13 提出四条,本文逐条回应。

| | 需求 | 结论 |
| --- | --- | --- |
| **R1** | 一个模型配多个 provider,不可用时自动路由到下一个 | 做。这是本方案的**唯一**核心理由(见 §2) |
| **R2** | 用「多配置文件 + 指针」替代复写式切换,避免写坏配置 | 做,而且更彻底:**配置只写一次,之后永不再改**(决定 34) |
| **R3** | Codex 先官方登录(保留插件/远程),本地把 provider 换掉 | **已实现,且不需要 router**(§2.1) |
| **R4** | 合买订阅 + VPS 反代的远端共享拓扑 | VPS 只做纯反代,在本地 router 眼里就是队列里的一个 provider(决定 3) |

**关键事实:这些能力在本仓库的 CC Switch 时代全部实现过。** schema v21 删除的九张退役表里
有四张直接属于代理/故障转移(`proxy_config`、`proxy_live_backup`、`provider_health`、
`stream_check_logs`)。所以这不是从零发明,而是**恢复已删功能 + 针对旧实现的失败模式
重新架构 + 接入本 app 独有的配额数据**。

### 1.1 旧实现为什么「难用、经常出错」

用户对 CC Switch 的不满,根因有四条,新方案逐条避开:

| 旧实现的问题 | 新方案 |
| --- | --- |
| **复写式切换**:每次切换整段改写 CLI 配置,依赖备份/恢复 | 配置只写一次(决定 34) |
| **代理常驻 + 全量请求日志**:与低功耗目标冲突 | 无轮询、不记全量日志(§6) |
| **熔断不感知配额**:不知道订阅窗口和 key 余额 | 接入现有配额数据——但只作辅助(决定 16) |
| **健康检查靠轮询** | 纯失败反馈驱动,零定时器(§6) |

## 2. 已经排除的选项(2026-08-14 实测)

**这一节最重要**:它把「为什么需要 router」这个前提改了。读后面任何内容之前先读这里。

### 2.1 router 不是「官方登录 + 自己的 provider」的前提

用户最初要 router 的理由是 R3。当天在他本机逐步实测,结论是**纯配置就能做到**:

```toml
[model_providers.packyapi]
name = "packyapi"
base_url = "https://www.packyapi.ai/v1"
wire_api = "responses"
requires_openai_auth = true            # 维持官方会话 → 远程 + 插件可用
experimental_bearer_token = "..."      # 模型请求的实际认证
```

**两个键都要**,少任一个坏不同的一半:

- 只有 `experimental_bearer_token`:模型能用,**远程与插件静默失效**(极易误判)
- 只有 `requires_openai_auth`:模型请求带着官方 OAuth token 发给第三方,被拒 401

`auth.json` 全程不用动;provider id 不是关键(`openrouter` / `custom` 都行)。
详见 `HANDOFF.md` §13。

**抓包实测:官方 OAuth token 不外泄。** 把 `base_url` 临时指向本地一次性监听,抓一次
真实请求的头(只对头值算 sha256 与已知凭据比对,不打印不落盘):`Authorization` 里是
中转的 bearer token,官方 access / id / refresh token 与 account_id 一个都没出现。
(`x-oai-attestation` 头未纳入比对,内容未知。)

**于是 router 只剩两条理由**:

1. **自动故障转移**——纯配置做不到,必须有东西在请求路径上
2. **纵深防御**——把官方凭据拦在 localhost。但实测显示当前**并没有在漏**,所以这条是
   「以防万一」,不是「正在出血」

### 2.2 不放云端

用户问过「放 VPS 上跑 LiteLLM 是不是更好」。**不。**

决定性理由:用户要把**官方登录也当作队列里的一个 provider**,那 router 就得能用
ChatGPT 的 OAuth 凭据发请求——放云端等于把订阅账号凭据长期存在 VPS 上。
次要理由:额度数据全在本机,云端看不到。

**VPS 若真搭了,它就是列表里的一个 provider**,不是本地方案的替代品。

### 2.3 v1 不做协议转换

理由**不是性能**——转换约 30–40 ms/次、6 秒 CPU/天,仍是噪声。理由是**维护成本**:
工具调用形状不同、reasoning 在 Chat 侧可能无对应物、流式事件生命周期要跨块维护状态、
两边持续加字段导致转换器腐烂。仓库历史里那串补丁(web_search 黑名单、
`base_instructions` 必填、`supportsParallelToolCalls`)就是疤。

「同协议就跳过转换」的折中也一并否掉:只要队列**可能**混协议,转换器还是得写得维护,
跳过只省运行时那几十毫秒——复杂度按「做」算,收益按毫秒算。

代之以**决定 20**:配置里记录每家的协议,**在配置阶段就拦住混协议的队列**,把未来的
运行时诡异故障变成配置时一句看得懂的错。

## 3. 架构与生命周期

| # | 决定 |
| --- | --- |
| 1 | **要**自动故障转移 |
| 2 | router 放**本地**(理由见 §2.2) |
| 3 | VPS 若搭了就是**队列里的一个 provider** |
| 4 | **router 跑在 app 进程里**。用户判断:退出/升级那几十秒的暴露可以接受,app 是开机自启常驻的。**否决了** LaunchAgent 独立服务 |
| 5 | 四条保险:①**崩溃隔离**(每连接一个任务,panic 不上冒——router 是新代码在处理网络输入,不能带着 app 一起死);②启动时**先开监听端口**再做其他初始化;③**退出前提示**;④**逃生门**,见决定 37 |
| 6 | router 写成**独立模块**,不与界面缠绕。以后想改成独立服务是改打包方式,不是重写 |
| 34 | **config.toml 的指针写一次之后永不再改**,永远指向 router。手动切换改的是 **router 内部的选择**,不是配置文件 |
| 35 | **撤销「app 退出时把指针改回直连」** |
| 36 | app 启动时若发现指针不是自己写的:**不静默覆盖**,标记「这段有缺口」、把受影响 provider 的估算标成不完整,并提示用户 |
| 37 | **逃生门不能只存在于「需要 app 活着才能用」的地方**。必须有一条命令行回退方式并写进文档——app 都挂了,app 里的按钮点不了 |

**决定 35 的由来**:曾设计「app 退出时把指针改回直连」以换取「app 挂了 codex 还能用」。
代价是绕过 router 变成**设计里的常态**(那段用量没有归因)、要补一整套指针时间线机制、
而且**复写配置又回来了**——而消灭复写正是 R2。这笔账不划算,撤销。

于是**会计漏洞消失**:流量永远经过 router,记录永远完整,不需要时间线也不需要持续
监听 config.toml。逃生门降级为「router 彻底坏掉时的自救」,缺口从「每天都在漏」变成
「自救那段时间没记录」。

## 4. 路由逻辑

### 4.1 模型与 provider 的对应

| # | 决定 |
| --- | --- |
| 7 | 朝 Codex 那端**用它内置的模型 ID**,不发明新名字,因此**不需要**生成 Codex 模型目录 |
| 8 | 录入分两步:**先加 provider**(带模型清单),**再按模型排顺序** |
| 11 | 模型清单:能自动拉就自动(中转一般有 `/v1/models`,但格式各家不同),**手动贴保底**——手动是保底不是降级 |
| 12 | **表里一行不带开关**(不要协议/web_search 之类的每行开关),先做最简版 |
| 22 | v1 **照样需要「哪家有哪个模型 + 真实模型 ID」**——切过去的那家未必有这个模型(官方就没有 `sol`),不知道就只是换个地方 400 |

### 4.2 失败与降级

| # | 决定 |
| --- | --- |
| 13 | 拉黑单位 = **表里一行**(模型 × provider)。正好治「官方没有 sol 但有 5.5」;只有连不上/超时这类与模型无关的失败才拉黑整个 provider |
| 14 | **换下一家**:连不上、超时、429、5xx、明确「没这个模型」的 4xx。**不换**:其余 4xx(认证错、参数错、内容被拒)——换一家只是把同一个错再挨一遍 |
| 15 | 流式**已经吐字之后不换**,把错误透给 CLI。否则用户会看到半句 + 另一句拼在一起 |
| 16 | 额度过滤**不是**主力,**撞几次拉黑**才是。额度数据空闲基线 15 分钟才刷一次,最坏情况会朝死路撞 15 分钟 |
| 10 | **严格按顺序,不做负载均衡**。注意 **LiteLLM 同名条目默认是负载均衡**,照抄它的配置概念会拿错默认行为;这里要的相当于 LiteLLM 的 `fallbacks` |

### 4.3 自动 / 手动两个模式

原来的问法是「手动选择到底是置顶还是锁定」。用户给了更好的答案:**把意图做成显式的
模式,而不是从一次点击里猜。**

| # | 决定 |
| --- | --- |
| 28 | 拉黑在 UI 上显示为「**暂不可用 · 还有 X 分钟**」。两个模式都显示:自动模式下解释「为什么跳过了这家」,手动模式下只是提示 |
| 29 | **两个模式**。自动(默认):按配置顺序,失败自动换,拉黑生效。手动:只用你选的那一家,**不自动切换**,失败就是失败,拉黑只显示不生效 |
| 30 | **必须能看出实际在用哪家**(菜单栏)。否则自动降级后用户以为在官方上,账单出现在中转那边 |
| 31 | **手动模式必须持续可见**,不是切换时提示一下。否则切了忘了,某家挂了没自动换,会被误判成「故障转移坏了」 |
| 32 | 手动模式下**照样记录失败,只是不据此行动**。切回自动时健康信息还在 |
| 33 | **不做「N 小时后自动切回自动模式」**。用户切手动就是要自己说了算,系统不该偷偷把方向盘拿回去 |

「手动模式」就是之前纠结的那个「锁定」,只是它是一个**模式**而不是每家一个 flag。
它也正好实现了用户描述的行为:「就算标注了暂不可用我依旧可以切换,我发现不行了自己
会换回去的」。

### 4.4 v1 范围,以及到 v2 的路

| # | 决定 |
| --- | --- |
| 21 | **v1 只做「一个全局 provider 顺序」**,每模型独立排序降到 v2 |
| 9(v2) | **每个模型的 provider 顺序可以不同**(sol 优先官方、luna 优先中转) |
| 23 | **硬约束**:路由决策函数必须返回「**这个模型的候选队列**」,不能返回「当前的 provider」 |

```rust
// 这样写，v2 只是给 order 多一个来源
fn candidates(model) -> Vec<(Provider, 真实模型ID)>

// 这样写，v2 就是重写
fn current_provider() -> Provider          // ← 禁止
```

第二种把「全局只有一个当前 provider」焊进签名,所有调用方都会跟着这个形状长,到 v2
每个调用点都要改。**代价为零,只是写的时候多想一步。**

v2 要加的只是一个 `??`:`order(模型 M) = 该模型的专属顺序 ?? 全局顺序`。

**顺带定下的语义**:换家之后下次请求**仍从头评估队列**;「继续用第二家」由**拉黑**
产生(冷却期内自然被跳过,冷却结束自动恢复试探),不需要额外的「当前是谁」状态。

## 5. 与监控侧的关系

### 5.1 为什么「router 不记 token」不成立

会话日志摄入是这样绑定的:

```rust
db.with_bound_usage_source("codex", provider_id, ...)
```

**Codex 的会话用量被整体绑定到一个 provider**,不区分某次请求实际走了哪家。于是:
日志有 token 没归属,router 有归属没 token——**谁都答不出「packyapi 用了多少」**。

### 5.2 修正后的决定

| # | 决定 |
| --- | --- |
| 17′ | **router 记 token**(唯一同时知道 token 与 provider 的地方,token 就在响应体的 `usage` 里),但**独立成表**,语义是「按 provider 分账」 |
| 24 | 会话日志那份继续管**总量**(覆盖不走 router 的部分);两张表**回答不同问题,UI 上不相加** |
| 25 | **余额优先问 provider 的 API**——权威,且覆盖用户在本机之外的消耗 |
| 26 | 没有余额 API 的:用 router 累计 + **用户录入、可编辑的价格表**估算。仓库已有 `provider_model_pricing` 可扩展 |
| 27 | 估算值**必须与接口读数视觉可辨**,且注明**只计经过 router 的部分**——它是**下界**,不是余额 |
| 18 | **429 反过来喂给额度监控**:router 是最先知道限流的一层,且拿得到 `Retry-After`,比 15 分钟轮询更快更准且不额外发请求 |

第 27 条不是洁癖:估算永远偏低(同一个 key 在别处的消耗看不见),两者长得一样的话,
迟早会拿一个下界当余额用,然后突然欠费。

### 5.3 UI 形态

按量计费 provider 的卡片有**上下两条量表**:

```
今日花费    $3.20 / $10.00      ← 流量：每天归零，分母是用户设的每日限额
▓▓▓░░░░░░░

余额        $61.40 / $100.00    ← 存量：只减不增，分母是参考额度
▓▓▓▓▓▓░░░░
上次充值 $100 · 2 分钟前更新
```

- 分母来源:接口能读就读;读不到由用户手动设(通常是「上次充值的金额」)
- **分母会过期**:接口读数发现余额**变大**时应视为充值,把分母自动重置成新余额;
  否则充值后进度条会显示 180%
- 两条性质不同(流量 vs 存量),视觉上要能区分
- 估算卡片:徽章 + 虚线边框 + 暖色,一眼看出不是读数

订阅型 provider **不适用**这个布局——它没有余额概念,继续用现有的窗口量表。

## 6. 能耗与内存(已量,不构成否决理由)

### 6.1 基准(2026-08-14 实测)

```
LLM Usage Bar(当时安装的 2026-08-07 构建)
  RSS 38.1 MB ｜ 运行 12h29m ｜ 累计 CPU 46m28s
  → 平均 6.2% → 约 5,360 秒 CPU/天
```

**顺带发现**:该构建早于 HANDOFF §11.3 那五项功耗优化(8/13 才合完),用户跑的是
未优化版本。**已于 2026-08-14 重新构建安装。**

### 6.2 内存

router 跑在 app 进程内,tokio 运行时已存在,边际成本三块:

| | 大小 |
| --- | --- |
| 监听器 + 路由表 + 拉黑状态 | < 1 MB |
| 每个进行中的请求(纯流式转发) | 几十 KB |
| 每个进行中的请求(**要能重发**) | 等于请求体大小 |

第三行是故障转移**本身要求**的。实测单个请求体 **58 KB**,但 Codex 每轮重发整段对话,
长会话会涨到几百 KB 至几 MB。

**决定 15(已吐字之后不换)天然限制了它的寿命**——缓冲只需留到第一个字节回来,
通常 1–3 秒。峰值几 MB、存活几秒。

### 6.3 CPU

**空闲为零**——监听 socket 挂在 kqueue 上不产生唤醒,这与轮询有本质区别。

每个请求:改模型 ID(解析 58 KB JSON)≈ 1.8 ms + TLS 握手(连接复用后摊薄)2–5 ms
+ 搬字节(微秒级)= **2–8 ms**。按 200 次/天 ≈ **1 秒 CPU/天**,对照 6.1 差三到四个
数量级。

### 6.4 真正该防的三件事(都不是吞吐)

1. **连接泄漏**——内存与文件描述符稳定爬升,这才是现实的失败模式
2. **绝不加定时器**——任何心跳/健康检查的定时器都会阻止系统进入空闲(§11.3 的教训)
3. **缓冲上限**——建议 4 MB,超过退化成不可重发的纯流式

---

## 7. Non-goals

- **不缝 LiteLLM**(本地与远端 v1)。本地:Python 常驻服务与低功耗前提冲突;
  远端:VPS 只做纯反代,仅在出现滥用/分账需求时才升级为网关(虚拟 key + 限额),
  **仍不开它的 router/fallback**——路由决策始终在本地
- **不做负载均衡 / 流量镜像 / 多机同步路由状态**
- **不做 CC Switch 式切换模型**(不按需反复改写 CLI 配置)
- **不做 MCP / prompts / skills 管理**(与 v21 删除保持一致)
- **不做轮询健康检查**

### 7.1 已查证的第三方事实

- **Claude Code**:官方 llm-gateway 文档写的是不支持把 Claude Code 路由到
  **非 Claude 模型**。**注意**:路由到「同一模型的不同供应商」(即常规的
  `ANTHROPIC_BASE_URL` 中转用法)不在这句话射程内——初版草案把这两件事混为一谈,
  对 Claude Code 的判断过于悲观
- **Gemini CLI**:自带模型级 fallback,但仅限 Gemini 自家模型之间,不跨 provider
- **Codex 监控侧**:提供第一方只读 RPC(`codex -s read-only -a untrusted app-server`,
  暴露 `account/read`、`account/rateLimits/read`),监控侧读额度可优先用该通道,与路由无关

## 9. 落地阶段(若批准)

| 阶段 | 内容 | 出口条件 |
| --- | --- | --- |
| **1** | 一次性指针 + loopback 转发 + 请求归因落库 + fail-closed | Codex 走本地路由完成一次真实请求;归因出现在用量面板;指针写入/回退有测试 |
| **2** | 全局 provider 顺序 + 冷却/拉黑 + 自动/手动模式 | 主 provider 故障时自动切备用;手动模式不自动切换且持续可见 |
| **3** | 每模型独立顺序(决定 9)、队列编辑 UI、菜单栏状态 | 每个模型可有不同顺序;菜单栏显示实际在用哪家 |

**阶段 1 的性价比要单独评估**:它把「codex 依赖 router 活着」这个代价全付了,却不含
自动切换。而它交付的「不用再改配置」,不建 router 也能拿到(§2.1)。
**建议阶段 1 之后真的停下来用一段时间**,再决定是否进阶段 2。

## 10. 仍然敞着的

- **用户自己的疑惑尚未全部提出**——他 2026-08-14 明确说过还有,不要跳过
- 拉黑多久、要不要半开试探(可照搬旧实现默认值:4 次失败 / 60 秒 / 恢复试 2 次)
- 重试次数与 CLI 侧重试的叠加(叠加会放大延迟)
- 归因表的具体形状(在 17′ 的前提下设计)
- `x-oai-attestation` 头里是什么(§2.1 未验证的那项)
- 用户的 `codex-provider` 脚本是否会**恢复** `auth.json`——若会,重新登录后再切一次
  provider 会把 refresh token 打回旧状态、再次触发「already used」
