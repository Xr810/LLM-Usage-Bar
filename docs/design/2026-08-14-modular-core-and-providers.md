# 模块化:一个 core + provider 模块 + 多个前端面板

> **状态:讨论产物,未批准。** 2026-08-14 与用户讨论后整理,不是已批准的规格,
> 也没有排期。与 [`2026-08-14-local-routing-design.md`](2026-08-14-local-routing-design.md)
> 正交——本地路由做不做、怎么做,都不影响这份的结论。

---

## 1. 用户要的是什么

原话:「一个 core + 各种 provider 插件 + 目前两种未来可能增加的前端面板」。
动机有两条,**它们是不同的两件事**,早先的讨论一度只答了第一条:

1. **好添加** —— 以后接一个新 provider / 新 agent 要轻松
2. **好卸载** —— 「我如果后续不用 Codex 或者 Claude Code 了」,要能干净地拿掉

第 2 条才是真正的难点,也是本文的目标。

## 2. 把目标变成一个可以量的数

> **删掉对某个 provider 的支持,要动几个文件?**

这个数才是要优化的东西,而且它**与「用不用插件机制」无关**——耦合很深的插件系统照样
删不掉,模块划得干净的普通代码删起来就是删个文件加删一行注册。

### 2.1 今天的基线(2026-08-14 实测,以 Codex 为例)

| | 提到 `codex` / `Codex` 的文件数 |
| --- | --- |
| 后端 `src-tauri/src` | **62** |
| 其中 `database/` 层 | 12 |
| 前端 `src` | **34** |
| 其中真实逻辑 | 14 |
| 其中测试 | 11 |
| 其中类型 / schema | 5 |
| 其中 i18n 文案 | 4 |
| **合计** | **96** |

「提到」不等于「依赖」——i18n 文案和测试的拆除成本远低于数据库 schema。但 96 这个数
本身说明问题:**Codex 这个概念渗进了每一层**,包括本该完全不知道它存在的数据库层。

---

## 3. 划线:core 拥有不变量,插件拥有差异

| 归 **core**(所有 provider 一样) | 归 **provider 模块**(每家不同) |
| --- | --- |
| 什么时候刷新(空闲间隔、活动触发、去抖) | 凭据在哪、怎么读 |
| 失败怎么退避、429 冷却、拉黑规则 | 打哪个端点、带什么头 |
| 数据库、schema、迁移 | 响应怎么解析 |
| 归一化数据模型(额度窗口、余额、用量事件) | 会话日志怎么解析 |
| 用量摄入流水线(盯文件 → 增量读 → 去重 → 写库) | 该家的模型清单怎么来 |
| 对面板的数据契约 | |
| 路由决策(队列、优先级、故障转移) | |

用户的疑虑是「openai / claude / packy 取额度的方式都不一样,所以该做成插件」——
对,但**差异恰好只在右边这一列**。左边整列是共用的,而其中一部分现在被复制在各家
的代码里。**把左列收进 core,正是这次模块化的主体工作。**

core 内部**自己**又该分成哪几块,见 §9。

---

## 4. 硬纪律:core 里不能出现任何 provider 的名字

做这类重构最大的风险是 core 长成一个什么都知道的大泥球——因为「共用」很容易被理解成
「凡是两家都要的都塞进去」,塞着塞着 provider 的概念就漏进 core 了。

所以给一条**能自动检查**的规矩:

> **core 里出现 `codex` / `claude` / `gemini` 等 provider 名字 = 漏了。**

可以写成一个 lint,性质与仓库现有的 `productIdentity` 扫描相同(而且那套刚在
2026-08-14 改成按内容 + 次数锚定,可以直接借鉴写法)。

**今天这条被严重违反**:`database/schema.rs`、`database/migration.rs`、
`database/backup.rs` 里都有 Codex——数据库层本该完全不知道有这个东西。
这也正是那 96 个文件里最难拆的部分。

## 5. provider 模块与面板是两种东西,方向相反

这一点必须先说清楚,否则容易得出「面板也该做成插件」的错误结论,白做一套加载机制。

```
        ┌────────────┐   ┌──────────────┐
        │ React 面板 │   │ SwiftUI 面板 │    ← 客户端：主动连上来
        └─────┬──────┘   └──────┬───────┘
              └───── 数据契约 ───┘
                       ↓
              ┌────────────────┐
              │      Core      │        ← 调度、存储、归一化模型、路由
              └───────┬────────┘
                      │ core 主动调用它们
        ┌────────┬────┴────┬──────────┐
      claude   codex    gemini    packyapi     ← provider 模块：被调用
```

| | provider 模块 | 前端面板 |
| --- | --- | --- |
| 谁调用谁 | **core 调用它** | **它调用 core** |
| 谁管生命周期 | core | 自己 |
| core 知道有几个吗 | 知道,要遍历 | **不知道,也不需要知道** |
| 加一个要改 core 吗 | 注册一行 | **完全不用** |

**所以面板不需要任何「插件机制」**——它已经是最松的耦合。加第三个面板 = 照着现有
契约写一个新客户端,core 一行不动。SwiftUI 壳现在就是这么接上去的。

只有 provider 模块需要「定义接口 + 注册 + 可增删」这一套。

### 5.1 两个面板的实际形态(别一概而论)

| | 在哪跑 | 怎么与 core 通信 |
| --- | --- | --- |
| React 面板 | Tauri 的 webview 里,**与 core 同一个 app** | Tauri IPC(`invoke(...)`) |
| SwiftUI 面板 | **独立进程**(另一个 app) | 本地 socket + 版本化 JSON |

只有 SwiftUI 是独立进程。它必须独立,因为原生 app 与 Tauri 是两个运行时,塞不进同一个
进程;这条线的目的是按绞杀者节奏逐步替换 webview,**过渡期两个面板会并存**——这正是
「面板可能有多个」的现实来源,不是假设。

### 5.2 为什么是「面板调 core」而不是反过来

1. **真相在 core 手里**:数据在它的库里,额度是它采的,路由是它决策的。面板是视图,
   视图向数据要东西
2. **面板可以不存在**:用户平时是菜单栏模式,主窗口根本没开。**core 必须在没有任何
   面板时正常工作**。若由 core 推,它就得维护「现在有没有人在听」这个状态
3. **面板可能有好几个**:拉模型下两个面板互不知道对方存在;推模型要维护订阅者名单

**补充**:core 也会广播(代码里的 `app.emit("usage-cache-updated", ...)`)——数据变了
喊一嗓子,面板听见再来拉。但 core **从不针对某个面板做事,也不知道谁在听**,依赖方向
仍是单向的。

---

### 5.3 core 与面板之间怎么传数据(2026-08-14 认可)

分两条通道,按「数据大小 × 是否常显」分,**不是一刀切**:

| | 谁更新 | 方式 |
| --- | --- | --- |
| **菜单栏托盘** | core **直接推** | 进程内直接改托盘标题,50ms 合窗(同一批变化只更新一次) |
| **面板数据** | core **广播,面板拉** | core 发 `usage-dashboard-invalidated`,面板听见再取自己要的那部分 |

**面板这条不是轮询**——面板没有定时器,挂在事件上睡觉,core 喊一声才醒。这与
HANDOFF §11.3 修掉的那类「每 300ms 醒一次」是两回事。

#### 为什么事件里不带数据

「广播 + 拉」看起来比「直接把数据推过去」多一次往返,但后者更贵:

> **core 得为每个监听者把数据序列化出来,不管对方在不在看。**

而这个 app 的常态是**只有菜单栏、主窗口关着**。那种状态下:

- 现在:core 喊一声,没人拉(窗口没开)→ 结束
- 带数据推:core 认真序列化一份面板数据 → 发出去 → 没人看 → 扔掉

要避开这份浪费,core 就得知道「谁现在在看什么」——那就是维护订阅者状态,正是
§5 想避开的东西。

**托盘之所以直推,恰恰因为它不同**:一直可见、数据极小、且在同一进程里,没有序列化
也没有往返。所以这套设计是有意的混合:**小而常显的直推,大而按需的广播 + 拉。**

#### 一个反例(2026-08-14 已修)

`src/lib/query/providerUsageActivity.ts` 的活动热力图曾带 `refetchInterval: 5 分钟`
——定时拉,不管数据有没有变。而且「关闭即最小化到托盘」意味着窗口只是被隐藏、
webview 仍然活着,**定时器在没人看得见的情况下继续每 5 分钟查一次库**(一天 288 次)。

后端明明已经有 `usage-dashboard-invalidated`,面板别处都接了,只有这块退回了轮询。
已改为跟别处一致:去掉 `refetchInterval`,由 `useUsageEventBridge` 一并失效。
量级不大(约一两秒 CPU/天),但它与 §11.3 那批优化是同一类账,且改动很小。

**规则**:面板侧不应出现任何 `refetchInterval`。数据什么时候变,由 core 说了算。

---

### 5.4 菜单栏:唯一的常驻面,它承担什么

菜单栏在这套架构里地位特殊,**它不是"面板之一",而是应用的默认状态**:

- 用户平时主窗口是关着的(关闭即最小化到托盘),**菜单栏是唯一一直看得见的东西**
- 它由 core 在进程内直接更新,不依赖任何面板存活(§5.3)
- 因此它是**唯一可以承诺"一定看得到"的位置**——任何"必须让用户知道"的状态都得落在这里

#### 它必须显示什么

| 内容 | 来源 |
| --- | --- |
| 当前用量摘要 | 现有行为 |
| **实际在用哪个 provider** | router 文档决定 30——自动降级后若不显示,用户会以为在官方上,而账单出现在中转那边 |
| **处于手动模式的常驻标识** | router 文档决定 31——不显示的话,切了忘了,某家挂了没自动换会被误判成"故障转移坏了" |
| **router 不在路径上**(逃生状态) | router 文档决定 36 |

这四条的共同点:**它们都是"用户不知道就会误判"的状态**,而不是锦上添花的信息。
判断某个状态该不该上菜单栏,用这一条来筛。

#### 它不承担什么

**菜单栏是显示面,不是配置面。** 07-16 的设计已明确左键弹窗不做配置动作,
本文沿用:切换 provider、改优先级、编辑价格表这些都在主面板里做。

理由与 §5.3 一致——菜单栏要保持"极小的数据 + 进程内直推",一旦让它承担配置动作,
它就需要回写、需要校验、需要错误处理,那份复杂度会把这条最可靠的通道弄脏。

## 6. 面板:provider 模块**不**自带界面

用户提到「目前两种未来可能增加的前端面板」(React 与 SwiftUI)。由此必须先回答一个
问题:provider 模块要不要自带 UI?

| | **模块只出数据**(选中) | 模块自带界面 |
| --- | --- | --- |
| 加一个 provider | 写一个后端模块 | 后端 + React 界面 + SwiftUI 界面 |
| 面板数量增加时 | 模块不用动 | **所有模块都要回炉补一套** |

必须选左边。否则现在两个面板,每加一个 provider 就是三份工作;将来加第三个面板,
已有的每个模块都得重做。

**代价(诚实说明)**:某个 provider 有前所未有的展示形态时(例如 router 讨论里
那个「上下两条量表」的按量计费卡片),需要**扩展归一化模型 + 两个面板各实现一次**。
这种情况少,而且新形态本来就得有人设计——插件化并不能省掉这份工作,只会把「写组件」
换成「写插件」再加一层壳。

**现状**:前端的 `SubscriptionProviderCard` 已经是数据驱动的(整个文件里厂商名只
出现 1 次),Swift 壳与 Rust 核心之间也已经是版本化的数据契约。这条线的方向是对的。

---

## 7. 「模块」不必是动态加载的插件

用户想要的属性是「一个模块 + 一行注册,删掉不影响别人」。**编译期模块就能给到**,
不需要维护插件 ABI、版本兼容和加载机制。

动态加载唯一的额外好处是「不重新编译就能装卸」——而本项目是从源码构建的,这个好处
等于零。

结论:先按模块做,把那个文件数降下来。做完之后再看还要不要真插件——大概率不需要。

## 9. Core 由哪几个模块组成(2026-08-14 认可)

### 9.1 现状:今天没有 core

后端现在是**按技术类型分的目录**,不是按职责分的模块:

| 目录 | 文件 | 行数 |
| --- | --- | --- |
| `database/` | 23 | 25,556 |
| `usage/` | 32 | 21,797 |
| `services/` | 26 | **21,650** |
| `commands/` | 19 | 10,138 |
| `credentials/` | 7 | 5,255 |

外加顶层散着 `claude_quota.rs`(2,842 行)、`tray.rs`(1,137 行)、`settings.rs`(1,325 行)等。

**最能说明问题的是 `services/`**:21,650 行,而这个名字不表达任何边界——什么都能塞,
事实上也确实什么都塞了(订阅额度、会话日志、Coding Plan、WebDAV 同步、Claude CLI
认证……)。一个目录叫「服务」等于没分类。

还有 `claude_quota.rs` 2,842 行**躺在根目录**——单个 provider 的东西在最顶层。

### 9.2 目标划分(按职责)

```
                    api
                     ↓
        route  ·  quota  ·  ingest
                     ↓
                   store
                     ↓
                   model
```

| 模块 | 管什么 | 今天散在哪 |
| --- | --- | --- |
| **model** | 归一化词汇表:用量事件、额度窗口、provider、余额、tier | `usage/domain.rs`、`services/subscription.rs` |
| **store** | 数据库、schema、迁移、DAO | `database/` |
| **ingest** | 盯文件 → 增量 → 去重 → 写库(**解析交给 provider 模块**) | `services/session_usage*.rs` |
| **quota** | 何时刷新、退避阶梯、429 冷却、活动触发 | `usage/quota.rs` |
| **route** | 队列、优先级、故障转移、拉黑 | 尚不存在 |
| **api** | 面板能查什么、能下什么命令、变更怎么广播 | `commands/` + Swift 那个 socket 桥 |
| **config** | 用户偏好、provider 配置、价格表 | `settings.rs` |
| **secrets** | 钥匙串 / 加密文件的安全存取**机制** | `credentials/` |

### 9.3 三条关键边界

**一、依赖必须单向,`model` 在最底下。**

`model` 谁都能依赖、它谁都不依赖。**只要 provider 的概念不进 `model` 和 `store`,
「删掉一个 provider」就永远是浅层操作。** 今天恰恰相反——`database/` 里 12 个文件
提到 Codex,这正是 §2.1 那 96 个文件里最难拆的部分。

**二、`secrets` 与 provider 模块的分工要划清。**

- 「凭据**怎么安全地存取**」(钥匙串封装、加密文件读写)→ **core**
- 「这家的凭据**放在哪、叫什么**」→ **provider 模块**

划错的话 core 里就会出现 `Claude Code-credentials` 这类字符串,又漏了(违反 §4)。

**三、`api` 必须与传输无关。**

这条最容易踩:`commands/` 一万行是 Tauri 命令,而 SwiftUI 面板走的是 socket。
**若契约直接长在 Tauri 命令上,socket 那边就得再写一遍。**

正确形状:`api` 定义「有哪些查询、哪些命令、广播什么」,Tauri 命令与 socket 各自
**只是它的一层薄壳**。这也正是 §5 那张图里「面板通过数据契约连上来」的落地方式。

### 9.4 最大的一块搬运

**`services/` 那 21,650 行要被拆散,分进上面几个模块。** 它不是「再拆一层子目录」
的问题——那个名字本身就该消失,因为它不表达职责。

## 10. 分步(按性价比排,未排期)

> **与 §9 的关系**:§9 是**目标形态**(全面重排成 model/store/ingest/quota/route/api/
> config/secrets,并让 `services/` 这个名字消失)。下面三步**不是**它的完整实施路径,
> 而是通往它的路上性价比最高的几段——先把 §2.1 那个文件数降下来,再决定要不要一次
> 走完全面重排。**不要把 §9 当成下一个迭代的范围。**


### 第一步:会话日志抽共享流水线(收益最大)

两家现在各写各的,但干的是同一套事:

```
盯文件变化 → 读增量 → 解析成用量记录 → 去重 → 写库
   ↑共享      ↑共享      ↑ 每家不同      ↑共享  ↑共享
```

**只有「解析」是每家不同的。** 接口划在这里,加一个 agent 就从「照着抄 1,500 行」
变成「写一个解析器」,而且现有那些增量、去重、分区处理的坑自动继承。

### 第二步:各家代码收进自己的模块

`subscription.rs` 按 provider 拆开。纯搬运,diff 大但风险低——**建议单独一次做完,
不要和别的改动混在一个提交里**(2026-08-14 已有教训:大改动混提交,出岔子时归因困难)。

### 第三步(远期):把 provider 概念请出数据库层

12 个文件,是真手术。等有明确需求再动,不要为了好看去拆。

**预期**:做完前两步,那个 96 大概能降到 20 上下。到那时再判断是否还需要真插件。
