# 模块化:一个 core + provider 模块 + 多个前端面板

> **状态:讨论产物,未批准。** 2026-08-14 与用户讨论后整理,不是已批准的规格,
> 也没有排期。与 [`2026-08-14-router-decisions-wip.md`](2026-08-14-router-decisions-wip.md)
> 正交——本地路由做不做、怎么做,都不影响这份的结论。

---

## 1. 用户要的是什么

原话:「一个 core + 各种 provider 插件 + 目前两种未来可能增加的前端面板」。
动机有两条,**它们是不同的两件事**,早先的讨论一度只答了第一条:

1. **好添加** —— 以后接一个新 provider / 新 agent 要轻松
2. **好卸载** —— 「我如果后续不用 Codex 或者 Claude Code 了」,要能干净地拿掉

第 2 条才是真正的难点,也是本文的目标。

## 2. 把目标变成一个可以量的数

> **删掉对某个 provider 的支持,要动几个文件?**

这个数才是要优化的东西,而且它**与「用不用插件机制」无关**——耦合很深的插件系统照样
删不掉,模块划得干净的普通代码删起来就是删个文件加删一行注册。

### 2.1 今天的基线(2026-08-14 实测,以 Codex 为例)

| | 提到 `codex` / `Codex` 的文件数 |
| --- | --- |
| 后端 `src-tauri/src` | **62** |
| 其中 `database/` 层 | 12 |
| 前端 `src` | **34** |
| 其中真实逻辑 | 14 |
| 其中测试 | 11 |
| 其中类型 / schema | 5 |
| 其中 i18n 文案 | 4 |
| **合计** | **96** |

「提到」不等于「依赖」——i18n 文案和测试的拆除成本远低于数据库 schema。但 96 这个数
本身说明问题:**Codex 这个概念渗进了每一层**,包括本该完全不知道它存在的数据库层。

---

## 3. 划线:core 拥有不变量,插件拥有差异

| 归 **core**(所有 provider 一样) | 归 **provider 模块**(每家不同) |
| --- | --- |
| 什么时候刷新(空闲间隔、活动触发、去抖) | 凭据在哪、怎么读 |
| 失败怎么退避、429 冷却、拉黑规则 | 打哪个端点、带什么头 |
| 数据库、schema、迁移 | 响应怎么解析 |
| 归一化数据模型(额度窗口、余额、用量事件) | 会话日志怎么解析 |
| 用量摄入流水线(盯文件 → 增量读 → 去重 → 写库) | 该家的模型清单怎么来 |
| 对面板的数据契约 | |
| 路由决策(队列、优先级、故障转移) | |

用户的疑虑是「openai / claude / packy 取额度的方式都不一样,所以该做成插件」——
对,但**差异恰好只在右边这一列**。左边整列是共用的,而其中一部分现在被复制在各家
的代码里。**把左列收进 core,正是这次模块化的主体工作。**

---

## 4. 硬纪律:core 里不能出现任何 provider 的名字

做这类重构最大的风险是 core 长成一个什么都知道的大泥球——因为「共用」很容易被理解成
「凡是两家都要的都塞进去」,塞着塞着 provider 的概念就漏进 core 了。

所以给一条**能自动检查**的规矩:

> **core 里出现 `codex` / `claude` / `gemini` 等 provider 名字 = 漏了。**

可以写成一个 lint,性质与仓库现有的 `productIdentity` 扫描相同(而且那套刚在
2026-08-14 改成按内容 + 次数锚定,可以直接借鉴写法)。

**今天这条被严重违反**:`database/schema.rs`、`database/migration.rs`、
`database/backup.rs` 里都有 Codex——数据库层本该完全不知道有这个东西。
这也正是那 96 个文件里最难拆的部分。

---

## 5. provider 模块与面板是两种东西,方向相反

这一点必须先说清楚,否则容易得出「面板也该做成插件」的错误结论,白做一套加载机制。

```
        ┌────────────┐   ┌──────────────┐
        │ React 面板 │   │ SwiftUI 面板 │    ← 客户端：主动连上来
        └─────┬──────┘   └──────┬───────┘
              └───── 数据契约 ───┘
                       ↓
              ┌────────────────┐
              │      Core      │        ← 调度、存储、归一化模型、路由
              └───────┬────────┘
                      │ core 主动调用它们
        ┌────────┬────┴────┬──────────┐
      claude   codex    gemini    packyapi     ← provider 模块：被调用
```

| | provider 模块 | 前端面板 |
| --- | --- | --- |
| 谁调用谁 | **core 调用它** | **它调用 core** |
| 谁管生命周期 | core | 自己 |
| core 知道有几个吗 | 知道,要遍历 | **不知道,也不需要知道** |
| 加一个要改 core 吗 | 注册一行 | **完全不用** |

**所以面板不需要任何「插件机制」**——它已经是最松的耦合。加第三个面板 = 照着现有
契约写一个新客户端,core 一行不动。SwiftUI 壳现在就是这么接上去的。

只有 provider 模块需要「定义接口 + 注册 + 可增删」这一套。

### 5.1 两个面板的实际形态(别一概而论)

| | 在哪跑 | 怎么与 core 通信 |
| --- | --- | --- |
| React 面板 | Tauri 的 webview 里,**与 core 同一个 app** | Tauri IPC(`invoke(...)`) |
| SwiftUI 面板 | **独立进程**(另一个 app) | 本地 socket + 版本化 JSON |

只有 SwiftUI 是独立进程。它必须独立,因为原生 app 与 Tauri 是两个运行时,塞不进同一个
进程;这条线的目的是按绞杀者节奏逐步替换 webview,**过渡期两个面板会并存**——这正是
「面板可能有多个」的现实来源,不是假设。

### 5.2 为什么是「面板调 core」而不是反过来

1. **真相在 core 手里**:数据在它的库里,额度是它采的,路由是它决策的。面板是视图,
   视图向数据要东西
2. **面板可以不存在**:用户平时是菜单栏模式,主窗口根本没开。**core 必须在没有任何
   面板时正常工作**。若由 core 推,它就得维护「现在有没有人在听」这个状态
3. **面板可能有好几个**:拉模型下两个面板互不知道对方存在;推模型要维护订阅者名单

**补充**:core 也会广播(代码里的 `app.emit("usage-cache-updated", ...)`)——数据变了
喊一嗓子,面板听见再来拉。但 core **从不针对某个面板做事,也不知道谁在听**,依赖方向
仍是单向的。

## 6. 面板:provider 模块**不**自带界面

用户提到「目前两种未来可能增加的前端面板」(React 与 SwiftUI)。由此必须先回答一个
问题:provider 模块要不要自带 UI?

| | **模块只出数据**(选中) | 模块自带界面 |
| --- | --- | --- |
| 加一个 provider | 写一个后端模块 | 后端 + React 界面 + SwiftUI 界面 |
| 面板数量增加时 | 模块不用动 | **所有模块都要回炉补一套** |

必须选左边。否则现在两个面板,每加一个 provider 就是三份工作;将来加第三个面板,
已有的每个模块都得重做。

**代价(诚实说明)**:某个 provider 有前所未有的展示形态时(例如 router 讨论里
那个「上下两条量表」的按量计费卡片),需要**扩展归一化模型 + 两个面板各实现一次**。
这种情况少,而且新形态本来就得有人设计——插件化并不能省掉这份工作,只会把「写组件」
换成「写插件」再加一层壳。

**现状**:前端的 `SubscriptionProviderCard` 已经是数据驱动的(整个文件里厂商名只
出现 1 次),Swift 壳与 Rust 核心之间也已经是版本化的数据契约。这条线的方向是对的。

---

## 7. 「模块」不必是动态加载的插件

用户想要的属性是「一个模块 + 一行注册,删掉不影响别人」。**编译期模块就能给到**,
不需要维护插件 ABI、版本兼容和加载机制。

动态加载唯一的额外好处是「不重新编译就能装卸」——而本项目是从源码构建的,这个好处
等于零。

结论:先按模块做,把那个文件数降下来。做完之后再看还要不要真插件——大概率不需要。

## 9. 分步(按性价比排,未排期)

### 第一步:会话日志抽共享流水线(收益最大)

两家现在各写各的,但干的是同一套事:

```
盯文件变化 → 读增量 → 解析成用量记录 → 去重 → 写库
   ↑共享      ↑共享      ↑ 每家不同      ↑共享  ↑共享
```

**只有「解析」是每家不同的。** 接口划在这里,加一个 agent 就从「照着抄 1,500 行」
变成「写一个解析器」,而且现有那些增量、去重、分区处理的坑自动继承。

### 第二步:各家代码收进自己的模块

`subscription.rs` 按 provider 拆开。纯搬运,diff 大但风险低——**建议单独一次做完,
不要和别的改动混在一个提交里**(2026-08-14 已有教训:大改动混提交,出岔子时归因困难)。

### 第三步(远期):把 provider 概念请出数据库层

12 个文件,是真手术。等有明确需求再动,不要为了好看去拆。

**预期**:做完前两步,那个 96 大概能降到 20 上下。到那时再判断是否还需要真插件。
