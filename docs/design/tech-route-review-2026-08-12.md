## 1. 这个应用是什么

一个 **macOS 菜单栏(menu bar / tray)应用**,用于统计 AI 编码工具的用量与花费:

- 读取 Claude Code / Codex / Gemini CLI 等工具写在本地的 JSONL 会话日志,解析出
  token 用量、模型、时间戳
- 读取订阅额度(Claude 的 5 小时/周窗口、Codex 的 OAuth 配额等)
- 调用各服务商的计费端点获取 API 花费
- 存进本地 SQLite,在菜单栏显示一个"红绿灯"指示剩余额度是否够用
- 点开有一个完整的用量面板(三个 Tab、热力图、趋势图、可穿透到每条请求)

**运行特征**(这是选型的关键背景):

- **常驻后台,99% 的时间处于闲置状态**——菜单栏只显示一个数字/颜色
- 用户主动打开面板是低频事件
- 全部数据本地处理,无服务端
- I/O 密集(读文件、读写 SQLite、HTTP),**计算量很小**

**核心诉求:低功耗、低内存。** 这是一个整天挂在笔记本上的常驻程序,耗电是首要指标。

## 2. 目前是怎么做的

### 2.1 技术栈

| 层 | 技术 |
| --- | --- |
| 桌面框架 | **Tauri 2** |
| 核心/后端 | **Rust** |
| UI | React 19 + TypeScript,跑在系统 WebView(macOS 上是 WKWebView) |
| 存储 | SQLite(schema 已迭代到 v26) |

Tauri 的特点是**不自带浏览器内核**,用系统提供的 WebView(macOS: WKWebView,
Windows: WebView2),因此比 Electron 显著更轻。

### 2.2 代码规模【实测】

| | 规模 |
| --- | --- |
| Rust 总量 | 94,476 行 / 132 个文件 |
| 其中与 Tauri 框架耦合 | 20,214 行 / 35 个文件(21%) |
| 其中平台无关的纯核心逻辑 | 约 74,000 行(79%) |
| Rust 测试 | 1,122 个测试标记 |
| 前端 | 24,515 行 TS/TSX,83 个组件 |

### 2.3 目前的运行时表现【实测】

在目标机器上对已安装的生产版本(v3.16.5)取样:

| 指标 | 数值 |
| --- | --- |
| 累计 CPU 时间 | 22 分 03 秒 |
| 运行时长 | 22 小时 45 分 |
| **平均 CPU 占用** | **1.62%** |
| 瞬时稳态 CPU(20 秒窗口采样) | 3.0–3.2% |

**对一个闲置的菜单栏应用而言,1.6% 的持续 CPU 占用偏高。** 它的真实代价不只是这

> 说明:采样期间机器上正在运行 Claude Code,会实时产生新的会话日志供本应用摄取,

## 3. 已定位的性能问题(与选型无关,但影响判断)

### 3.1 现象:UI 层不是耗电来源【实测】

按线程拆分 CPU 时间:

| 线程组 | 累计 CPU |
| --- | --- |
| WebView 相关(CVDisplayLink ×2、WebCore Scrolling、JavaScriptCore scavenger 等 6 个) | **0:00.00** |
| tokio worker + 临时派生线程(8 个) | **9:53** |

**WebView 相关线程的 CPU 时间是字面意义上的零。** 耗电全部发生在 Rust 后端自身的
数据采集循环里,与 UI 技术栈无关。

### 3.2 根因【实测】

应用每 60 秒执行一次会话日志同步。需要遍历的文件规模:

```
~/.claude/projects        71 个 jsonl,111 MB
~/.codex/sessions       1294 个 jsonl,2.2 GB
```

同步逻辑**本身是增量的**——按文件维度存了 (mtime, line_offset) 游标,内容未变则跳过
解析。但**游标是逐文件查库的**,即每个文件一次独立的 SQLite 查询。

因此每 60 秒产生:约 1,365 次 stat 系统调用 + 约 1,365 次 SQLite 查询,
折合**持续每秒约 23 次磁盘操作**。性能采样的调用栈中 `pread` 高频出现,与此吻合。

### 3.3 修复方向

用 FSEvents(macOS)/ ReadDirectoryChangesW(Windows)文件监听替代定时轮询;
游标改为一次批量查询;tokio worker 线程数封顶。

**这一项与本文的选型问题完全正交——无论最终选哪条路线都必须修。**

## 4. 需要评审的选型问题

### 4.1 问题的由来

项目方希望进一步降低功耗与内存占用,考虑放弃 WebView、改用原生 UI。由此引出两个
层面的选择:

1. **UI 层**:WebView(现状)vs 原生
2. **核心层**:Rust(现状)vs Swift

另有一个背景条件:**平台优先级是 macOS 优先,Windows 押后。** 项目方本人主要使用
Mac,但这是一个开源项目,不排除未来需要 Windows 支持,因此不希望把这条路彻底堵死。

### 4.2 候选方案

| 方案 | 核心层 | macOS UI | Windows 可行性 |
| --- | --- | --- | --- |
| **A(现状)** | Rust | React / WKWebView | 高——Tauri 原生支持,但 WebView2 比 WKWebView 重 |
| **B** | Rust | SwiftUI(经 FFI 调用 Rust 核心) | 中——核心可复用,UI 需另写一套 |
| **C** | Swift | SwiftUI | **低**——见 4.3 |
| **D** | Rust | Rust + objc2 直接调 AppKit | 高——核心与思路都可复用 |

### 4.3 关于方案 C 的 Windows 可行性

需要向评审者确认这一判断是否准确:

Swift 编译器自 5.3 起官方支持 Windows,**但 SwiftUI 是苹果专有且闭源,不存在
Windows 版本**。因此方案 C 下 UI 必然要为 Windows 重写——这一点与方案 B 相同。

更关键的判断是:**让 Swift 在 macOS 上具备优势的那些能力,恰恰全部来自苹果专有框架**
(URLSession、Keychain、FSEvents、Instruments、GRDB 对 Apple 平台的适配),
而这些在 Windows 上或不存在、或由完整度较低的 swift-corelibs-foundation 提供。

因此我们的判断是:**方案 C 下的 Windows 版本接近于重写整个应用,而非"移植核心 + 重写
UI"。** 请评审者确认或推翻此判断。

## 5. Rust vs Swift 作为核心层:实测对比

### 5.1 基准测试设计

用应用真实的 Claude Code 会话日志(37 MB,8,921 行,其中 3,916 条含 usage 记录),
在两种语言中实现等价的解析逻辑:

- 逐行读取 JSONL
- 反序列化,提取 `type` / `timestamp` / `sessionId` / `message.model` /
  `message.usage.{input_tokens, output_tokens, cache_read_input_tokens,
  cache_creation_input_tokens}`
- 累加 token,收集去重的 model 集合

Rust 侧:`serde_json` + `BufReader` 流式读取,`--release` + LTO。
Swift 侧:`Foundation.JSONDecoder`(Codable),`-O -whole-module-optimization`。

**两侧输出的 token 总数与记录数完全一致**,确认工作等价。

工具链:Rust 1.95.0 / Apple Swift 6.3.3。

### 5.2 结果【实测,各 3 次】

| | Rust (serde_json) | Swift (JSONDecoder) |
| --- | --- | --- |
| 解析耗时 | **17.1 / 18.0 / 21.8 ms** | **66.3 / 68.1 / 86.8 ms** |
| 该任务峰值 RSS | **3.5 MB** | 44.7 MB(见下方说明) |
| 空程序基线 RSS | **1.4 MB** | 5.5 MB |

**结论:CPU 上 Rust 快约 3.5–4 倍;运行时基线内存 Swift 高约 4 MB。**

### 5.3 关于内存数字的重要修正

Swift 版的 44.7 MB **不能直接与 Rust 的 3.5 MB 相比**——该实现一次性把整个 37 MB
文件读入内存,这 37 MB 是实现方式造成的,不是语言开销。扣除后真实工作集约 7.7 MB,
对 Rust 的 3.5 MB 约为 2 倍。

我们另写了一个流式 Swift 版本试图修正,但因 `Data.subdata` 的重复拷贝导致实现劣化
(355 ms),**该数字不具参考价值,已废弃**。

**因此内存方面可信的结论只有两条**:运行时基线 Swift 高约 4 MB;工作集约为 2 倍。
如果评审者认为一个实现良好的流式 Swift 版本能显著改善,我们愿意重测。

### 5.4 换算到真实负载【估计】

应用的同步是增量的,稳态下每分钟只解析新增的少量行,而非全量 8,921 行:

| 场景 | Rust | Swift | 差值 |
| --- | --- | --- | --- |
| 首次全量导入 2.3 GB(一次性) | 约 1.1 秒 | 约 4.2 秒 | 3 秒 |
| 稳态每分钟增量解析 | 约 0.05 ms | 约 0.2 ms | 0.15 ms |
| **折算日均 CPU 差异** | — | — | **不到 1 秒/天** |

作为对照,**第 3 节所述的轮询缺陷造成的浪费约为 1,382 秒 CPU/天**。

**两者相差约三个数量级。**

### 5.5 由此得出的初步结论(请评审)

**对本应用的负载而言,Rust 与 Swift 在运行时能耗和内存上的差异可忽略不计。**

Rust 确实快 4 倍,该测量是可靠的。但本应用的计算量太小,4 倍的差异作用在一个本就
接近于零的基数上。**能耗几乎完全由架构决定(唤醒频率、每次唤醒的扫描量),而非核心
语言。**

**测量的边界(请评审者注意)**:本基准只覆盖 JSON 解析——核心层最重的计算负载,但
不是全部。未覆盖:ARC 在其他代码路径上的引用计数开销、SQLite 层(两侧都是同一个 C
库)、HTTP 层(以 I/O 等待为主)。我们判断后两者不足以改变结论,但这是判断不是测量。

## 6. 两种语言在 macOS 上做核心开发的定性对比【估计】

以下为经验判断,未经本次测量验证,请评审者校正:

| 维度 | Rust | Swift | 我们的判断 |
| --- | --- | --- | --- |
| JSON 解析 | serde_json,业界最快之一 | Codable 有已知开销 | **Rust 明显占优**(已实测,4x) |
| HTTP | reqwest,依赖树较大 | URLSession 内置,自动处理系统代理/证书 | Swift |
| SQLite | rusqlite / sqlx | GRDB.swift | 大致持平 |
| Keychain / FSEvents / 系统通知 | 经 objc2、security-framework,大量 `unsafe`,文档薄 | 原生一等公民 | **Swift 明显占优** |
| 并发模型 | tokio,成熟稳定 | async/await + actor,写法更简洁,但模型近年持续演进 | Swift 易写,Rust 更稳定 |
| 性能分析工具 | rust-analyzer 好,async 调试困难 | **Instruments,含专门的能耗分析器** | **Swift 明显占优** |
| 生态广度 | crates.io,覆盖全面 | SPM 生态较小,偏 iOS/App 方向 | Rust |
| 语言长期稳定性 | edition 机制,向后兼容强 | 历史上有破坏性变更,跟随苹果优先级 | Rust |
| Windows 一等公民支持 | `windows-rs` 由微软官方维护 | 官方支持存在但生态小众 | **Rust 明显占优** |

其中我们认为对本项目最实际的三条:

1. **Instruments 的能耗分析器**——本项目的核心诉求就是低功耗,而这是苹果专门为此
   提供的工具。本次调查是靠 `sample` + `ps -M` 拼出来的,用 Instruments 会更快更准。
2. **Keychain 与 FSEvents 的原生支持**——本应用的 API key 存于 Keychain,且第 3 节
   的修复方案正需要 FSEvents。这两项在 Swift 侧是原生能力。
3. **JSON 解析性能**——方向相反,是 Rust 的强项,且正好落在应用最重的负载上。
